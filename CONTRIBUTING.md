# Contributing to CrateMate

Thanks for helping out! This guide covers setting up, making a change and getting it merged. For coding conventions, see [docs/CODE_STYLE.md](docs/CODE_STYLE.md). For how the app fits together, see [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## Ground rules

Every change has to keep these three rules:

1. **Never write to the DJ folder.** Rekordbox tracks files by path. Moving, renaming or retagging a file breaks the user's collection, along with their cues and grids. CrateMate only reads from that folder.
2. **No network access.** CrateMate works entirely offline, and the README's privacy section promises that.
3. **No third-party dependencies** without discussing them in an issue first. The app uses only Apple's frameworks.

## Setting up

You need macOS 14 or later and Swift 6 or later. The Xcode Command Line Tools are enough, and full Xcode works too. For the end-to-end test, you also need `ffmpeg` (`brew install ffmpeg`).

```bash
git clone https://github.com/bflip12/cratemate.git
cd cratemate
swift build
```

### Running the app

`iTunesLibrary` only works when the app is launched as a bundle through LaunchServices. Running `.build/debug/CrateMate` from a terminal fails with an XPC or permission error, so build the bundle and open it:

```bash
scripts/build-app.sh
```

```bash
open build/CrateMate.app
```

`build-app.sh` builds a release binary, wraps it in `build/CrateMate.app` and ad-hoc signs it. The signature lets macOS remember the Apple Music permission between builds. `--install` also copies the bundle to `/Applications`.

### Running the tests

Unit tests:

```bash
scripts/test.sh
```

To add the end-to-end test, first generate a fake tagged library and a sample Apple Music export:

```bash
scripts/make-test-library.sh /tmp/cratemate-test
```

Then run the tests against it:

```bash
scripts/test.sh /tmp/cratemate-test
```

The expected end-to-end result is 9 matched and 1 not found ("Nobody - Not In Library").

Use `scripts/test.sh` rather than plain `swift test`. With only the Command Line Tools installed, incremental builds can lose the Swift Testing macro plugin, and the script passes its path explicitly.

### Formatting

The code is formatted with [swift-format](https://github.com/swiftlang/swift-format), which comes with the Swift toolchain, using the settings in [`.swift-format`](.swift-format). Format your changes before committing:

```bash
scripts/format.sh
```

CI runs `scripts/format.sh --check` and fails on any difference.

## Project layout

| Path | What's there |
|---|---|
| `Sources/CrateMateCore/` | All the logic, with no UI: Apple Music reading, library scanning, matching, M3U writing. Covered by the tests. |
| `Sources/CrateMate/` | The SwiftUI app: the `AppModel` state object and the views. |
| `Tests/CrateMateCoreTests/` | Swift Testing tests for `CrateMateCore`. |
| `Resources/Info.plist` | The app bundle's Info.plist, including version numbers and the Apple Music usage string. |
| `Resources/AppIcon.icns` | The app icon, generated by `scripts/make-icon.sh` from `scripts/make-icon.swift`. |
| `scripts/` | Build, test, format, test-library and icon scripts. |
| `docs/` | Architecture and code style. |
| `docs/brand/` | The logo, wordmark, lockups and brand guidelines. See its [README](docs/brand/README.md). |

## Making a change

Every change, including the maintainer's, reaches `main` through a pull request. `main` is protected:

- Nobody can push to it directly or force-push it.
- A pull request can only merge once the **Lint, test and build** CI check passes on a branch that's up to date with `main`, and all review conversations are resolved.
- Pull requests are squash-merged, so each one lands on `main` as one commit, and the branch is deleted afterwards.

The steps:

1. **Open an issue first** for anything bigger than a small fix, so we can agree on the approach before you spend time on it. Matching changes especially, since a tweak that fixes one title can break another.
2. **Branch from an up-to-date `main`.** Name the branch for what it does: `fix/feat-in-artist`, `feature/search-by-album`, `docs/…`, `ci/…`.
3. **Add or update tests.** Every matching change needs a test with the real-world title that prompted it. If it's an end-to-end case, add it to `scripts/make-test-library.sh` and update the expected counts.
4. **Run `scripts/format.sh` and `scripts/test.sh`.**
5. **Update the docs** if behaviour changed: README for anything user-visible, `docs/ARCHITECTURE.md` for the design, `CHANGELOG.md` under **Unreleased**.
6. **Open a pull request** and fill in the template.

### Commit messages

- Write the subject in the imperative and keep it to about 72 characters, e.g. "Prefer the extended mix when lengths tie".
- In the body, explain *why* the change is needed, not just what it does. A reviewer should be able to understand the problem from the message alone.
- Make one logical change per commit. A formatting-only change goes in its own commit.

### Reporting a matching problem

The most useful bug reports for the matcher are concrete pairs. For each one, include:

- the song as Apple Music shows it: title, artist and length;
- the file CrateMate picked, and the file it should have picked: filename, title and artist tags, and length.

Please don't attach audio files. The metadata is all that's needed.

## Releasing

Maintainers only:

1. Update `CFBundleShortVersionString` (and bump `CFBundleVersion`) in `Resources/Info.plist`.
2. In `CHANGELOG.md`, move the **Unreleased** entries under the new version with today's date.
3. Make these changes on a `release/vX.Y.Z` branch and open a pull request titled "Release vX.Y.Z".
4. Once it's merged, tag the merge commit on `main` as `vX.Y.Z` and push the tag.
5. The tag starts the **Release** workflow. It checks that the tag matches `Info.plist` and has a `CHANGELOG.md` section, runs the tests, and builds the universal app with `scripts/build-app.sh`. It then packs the DMG with `scripts/make-dmg.sh` and publishes a GitHub release with that changelog section as its notes. The release has `CrateMate-X.Y.Z.dmg`, its `.sha256`, and `CrateMate.dmg`, which is what `releases/latest/download/CrateMate.dmg` serves.
6. Update the version and download size on the website.

To try the workflow without publishing a real release, push a tag with a suffix, such as `v0.1.0-rc1`. It becomes a pre-release, which the latest-download link ignores. Delete it afterwards with `gh release delete v0.1.0-rc1 --cleanup-tag`.

To build the DMG locally, run `scripts/build-app.sh`, then `scripts/make-dmg.sh`. The output goes to `build/`.

### Signing and notarization

Releases are signed ad-hoc for now, so on first launch macOS says it can't verify the app, and users click **Open Anyway** in **System Settings › Privacy & Security**. The release notes explain this. To ship notarized builds instead, add these repository secrets. The workflow then signs with Developer ID and notarizes and staples the DMG, with no other changes needed:

| Secret | What it holds |
|---|---|
| `APPLE_DEVELOPER_ID_P12` | The Developer ID Application certificate and key, exported as `.p12` and base64-encoded |
| `APPLE_DEVELOPER_ID_PASSWORD` | The `.p12` export password |
| `APPLE_NOTARY_KEY` | An App Store Connect API key (`.p8`), base64-encoded |
| `APPLE_NOTARY_KEY_ID` | That key's ID |
| `APPLE_NOTARY_ISSUER_ID` | The issuer ID shown with that key |

Locally, `CODESIGN_IDENTITY="Developer ID Application: …" scripts/build-app.sh` signs with the hardened runtime, and `make-dmg.sh` signs the DMG with the same identity.
